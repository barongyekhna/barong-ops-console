## 一句话:我们在做什么

做一个**自动化选品系统**。它持续不断地从亚马逊(通过 Keepa)把产品信息扒进一个"产品仓库",
然后在我需要的时候,用三个 AI 一层层筛选,告诉我**哪些产品值得做、哪些该扔掉**,
并且分清楚每个产品是适合放到**亚马逊**卖、还是放到我自己的**独立站**卖、还是两个都行。

我是个小卖家。所以这个系统的灵魂是:帮我找到**"门槛刚刚好"**的产品——
太难做的(要大资金、要认证、要专利)我做不起;太简单的(谁都能卖)又被卷到死。
我要的是那种**靠脑子和执行力(而不是靠砸钱)就能做出差异化**的产品。

## 为什么要这么设计(这些是故意的,别当 bug 改掉)

这是最重要的一节。下面每一条都是深思熟虑的决策,你照着实现就行,不要"优化"掉:

**1. "持续扒数据"和"AI 筛选"是分开的两件事,故意解耦。**
Keepa 扒数据很便宜(就是消耗点额度),可以 24 小时不停扒,扒进仓库。
但 AI(尤其是贵的那个 Opus)调用很贵,**绝对不能实时跑、不能对每个产品都跑**。
所以设计成:**数据是后台一直在攒的;AI 是我手动点"开始选品"时,才去仓库里已经攒好的数据上跑。**
这样两笔钱分开:扒数据的钱是稳定的小钱,AI 的钱是我按一下才花、而且只花在很少的产品上。

**2. AI 之前先用"代码规则"筛一遍,故意的。**
能用 if-else 判断的事(价格不在区间、毛利太低、价格在跌、命中违禁类目),
就用代码直接毙掉,**绝不浪费 AI 去看这些垃圾**。整个系统是个**漏斗**:
越往后、越贵的资源(规则→便宜 AI→贵 AI→人工),处理的产品越少。

**3. 三个 AI 不是同一个标准跑三遍,是三个不同的活,故意的。**
如果三个 AI 都问同一个问题,那就是浪费 + 混乱。我们让它们各问一个不同的问题(下面详述)。

**4. Serper(查 Google 搜索结果的工具)是手动触发的,而且只查仓库里已有的产品,故意的。**
Keepa 在后台一直把产品扒进仓库;Serper **不自动跑、不挂定时任务**。
我想查的时候才点一下,它就去仓库里拿那些已经扒好的产品,挨个去 Google 上查"这个词好不好排"。
**这一条尤其重要:不要给 Serper 加任何自动定时任务,不要让它去外面重新爬一遍。它只对仓库里现有的产品做检查。**

**5. 存的是"产品特征",不是 Keepa 的原始大数据,故意的。**
Keepa 一个产品的完整历史数据可能上百 KB 到几 MB,几百万个存下来会爆。
我们只抽取选品需要的那几十个字段(价格、排名、趋势、卖家数、评论等),每条才 1-2 KB,几百万个也才几个 GB。
这是**硬盘**问题不是内存问题,普通一台服务器轻松装下。原始大数据要留就丢到便宜的对象存储,不进主数据库。

**6. Minea / PiPiADS 这两个独立站选品工具,我们不写代码对接,故意的。**
它们**没有公开的数据 API**,是给人用鼠标点的网页工具。
所以系统里它们是"人工旁路":我自己在它们网页上研究,挑到好产品**手动填进数据库**。
**不要去给它们写 API 集成——那个 API 不存在。**

**7. 有两个"查搜索结果"的用途,千万别搞混。**
- **Serper 查的是 Google** → 服务于独立站的 SEO 选品。
- **亚马逊页面的"垄断指标"**(页一前三名的评论数、单一品牌占多少份额、页一有多少新品)
  → 这要查的是**亚马逊站内的搜索结果**,不是 Google,所以**不能用 Serper**,得用别的亚马逊数据源。
这两件事用的工具不一样,实现时分清楚。

## 整个系统怎么运转(讲个故事)

**后台一直在做的(便宜,自动):**
1. 系统每天用 Keepa 的"产品发现"功能,按类目、排名、价格、评论数等条件,捞出一批候选产品的编号(ASIN),扔进一个"待处理队列"。
2. 系统每分钟从队列里取出一小批(匹配 Keepa 的额度回血速度,不能一次性猛拉,否则会被限流),
   用 Keepa 把每个产品的详细数据扒下来,抽取成"特征",存进仓库。
3. 存进去的同时,代码规则立刻筛一遍:明显不行的标记成"已淘汰",可能行的标记成"通过规则"。

**我手动触发时做的(贵,按需):**
4. 我点"开始选品",系统从仓库里"通过规则"的产品中挑出来。
5. **第一个 AI(DeepSeek,便宜)** 走量初筛,把明显平庸的滤掉。(这步建议放夜里自动批量跑,省得我等。)
6. **第二个 AI(GPT)** 对活下来的产品,去读真实的页面、真实的差评、竞品广告,验证数据是不是真的、有没有可以改进的空子。
7. **第三个 AI(Opus,最贵但最强)** 只看最后剩下的几十个,做最终决策:这产品小卖家到底该不该做、怎么做、放哪个平台、有什么风险、下一步该验证什么。
8. 系统把最终选出的好产品推到我的 Telegram,我人工过目,满意的才去打样、采购。

**独立站的 SEO 选品(我手动点 Serper 时):**
9. Serper 去仓库里拿 Keepa 已经验证过"有需求"的产品,查它们在 Google 上好不好排。
10. 如果一个产品"亚马逊上有人买(需求真)+ Google 上没人好好做(容易排上去)",
    那它就是我独立站靠免费自然流量就能吃下的好品——这是这套系统的一招杀手锏(下面详述)。

## 三个 AI 各自干什么(大白话)

把它们想成一条流水线上的三个工人,各管一段,问的问题完全不同:

- **DeepSeek(第一关,便宜的量化筛子)**:只看数字。问的是"这堆数字综合起来,值不值得花更贵的 AI 细看?"
  它快、便宜、宽松,拿不准就放行。它不读文字、不做创意判断,纯靠数据把一大批降到一小批。

- **GPT(第二关,带上下文的侦探)**:会读真实内容。问的是"数字背后是真的吗?有没有真的破绽可以利用?"
  它去看真实的产品页、真实的差评(差评里反复骂的点,就是你能改进的机会)、竞品的广告。
  它的任务是验证数字没骗人 + 找出差异化的缺口。

- **Opus(第三关,下注的决策者)**:最贵、最强,只看最后几十个。问的是"我这个小卖家到底该不该赌这个产品,怎么赌?"
  它判断:这产品的门槛是"用钱砌的"还是"用本事砌的"(用钱砌的不碰,用本事砌的可做);
  差异化方案以我的资源能不能真做出来;把退货率、运费、仓储费都算进去后真实赚不赚钱;
  该放亚马逊还是独立站;最后给出能直接执行的行动建议。

**铁律:必须按 DeepSeek → GPT → Opus 的顺序走,绝不跳级,绝不让最贵的 Opus 去看没经过前两关筛选的产品。**

## 亚马逊 vs 独立站:两套完全不同的生意经

**这是全系统最容易做错的地方:不能用一套标准评判两个平台。**

- **亚马逊**:需求是**现成的**——人已经在亚马逊搜索框里找东西了。
  你赢的方式是:抢到搜索靠前的位置、突破"评论壁垒"(对手评论太多你就挤不进去)、用更好的页面胜出。
  关心的核心指标:销量(看排名 BSR)、竞争对手数量、有没有大品牌垄断、利润能不能扛住亚马逊的各种费用。

- **独立站**:需求是**你自己搞来的**。独立站没人主动来搜你,流量靠两种方式:
  - **花钱投广告**(广告子路):产品必须有"3 秒钩子"——刷到广告 3 秒内就能让人心动或看懂它解决什么问题,
    而且毛利必须够高(≥60%),因为差价要拿去养广告。
  - **靠 SEO 自然搜索排上去**(SEO 子路):产品要对应一个"人们会去 Google 搜的问题",
    而且因为 SEO 排上去之后流量基本免费,所以**毛利要求可以放低**(≥40% 就行)——
    那些"广告养不起"的、利润薄一点但有人搜的产品,SEO 反而能做。

所以独立站其实分**两条子路、两套标准**,但最后都汇入同一个三个 AI 的流水线,只是给 AI 看的"判断手册"不同。

## 数据从哪来(大白话)

- **亚马逊数据 = Keepa**(有正经 API,可以全自动一直扒)。这是系统的主力。
- **Google 搜索结果 = Serper**(你已经有 key,便宜)。手动触发,查仓库里的产品好不好排 SEO。
- **关键词搜索量 = Google 的 Keyword Planner**(Serper 只给搜索结果、不给"这个词每月多少人搜",所以要补这个)。
- **趋势 = Google Trends**(看一个东西是在涨还是在跌,排除那种昙花一现的爆款)。
- **谁在投广告 = Meta 广告库 API**(免费,看竞品在 Facebook/Instagram 投了什么、投了多久;投得久=在赚钱)。
- **Minea / PiPiADS = 人工研究工具**(没 API,我自己上网页看,挑到的手动录入系统)。

## 一招杀手锏:Keepa × Serper

这是把"亚马逊数据"和"Google 数据"拼起来的聪明玩法,专门给独立站选品:

> **一个产品如果在亚马逊上卖得好(说明真有人要),但在 Google 上没人好好做这个词(说明我容易排上去),
> 那它就是我独立站能靠免费自然流量吃下的理想产品。**

用 Keepa 证明"有需求",用 Serper 证明"Google 上有空位"。两个条件同时满足的产品,
是那种**还没被同行(投广告的和做 SEO 的)同时盯上**的缝隙——这正是小卖家该钻的地方。

## 东西存哪、跑在哪

- 一台服务器(Hetzner CCX23,4 核 16G)就够同时跑你的 ops-console、数据库(PostgreSQL)和产品仓库。
- 现在**不需要**单独搞一台"仓库服务器",因为特征数据才几个 GB。等以后真的查询慢了再拆,文件里有怎么拆的说明。
- **所有流程都在 ops-console 里执行**(发现、富化、规则筛、三层 AI、Serper、推送),由 ops-console 自己的定时作业和后台 worker 驱动,不依赖任何外部编排工具。

## 给 Codex 的话:雷区与边界(请严格遵守)

1. **凡是文件里标了 `⚠️CONFIRM` 的数字,先去对应官方文档/接口核实真实值,不要自己猜一个写死。**
   比如 Keepa 各种操作的额度消耗、当前 Opus 的模型名称、Serper 的字段名。猜错了我又得返工。
2. **Serper 永远手动触发,绝不挂定时任务,只查仓库里已有的产品。** 不要让它自动去全网爬。
3. **不要给 Minea/PiPiADS 写 API 对接**,它们没有数据 API,在系统里是人工录入旁路。
4. **不要把"Google 搜索结果(Serper)"和"亚马逊站内搜索结果(垄断指标)"搞混**,用的是两个不同数据源。
5. **持续段绝不调用 AI**,AI 只在我手动触发的按需段跑。
6. **严格守住漏斗顺序**:代码规则 → DeepSeek → GPT → Opus,不跳级,最贵的资源处理最少的产品。
7. **每个里程碑先用少量真实数据跑通再放量**,别一上来就全量跑烧钱。
8. 缺失的字段(数据没拿到)不要直接判死产品,留给后面的 AI 判断,避免误杀。
