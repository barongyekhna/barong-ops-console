# RD 系列 · 远程桌面 运维手册

## 一句话

控制台里内置的「向日葵」:任何登录用户都能在网页上操控别人的电脑,但**必须对方在那
台电脑上点原生同意框**;自己的机器直接进;车间那种没人值守的机器可以标成公用机。

## 谁能当哪一端

| | 要求 | 说明 |
|---|---|---|
| **控制端** | 任何浏览器 | 只需要显示画面 + 发键鼠,浏览器本来就会。Mac / iPad / 手机都行,不装任何东西 |
| **被控端** | 装了控制台 Windows 客户端 0.4.0+ | 抓屏和注入键鼠要本机权限,这是操作系统的边界,绕不过去 |

第一期没有 Mac / 安卓被控端(苹果开发者账号未申请)。

## 通路:为什么不走 VPN

最初的设想是「两台机器都在 VPN 里,直接连内网 IP」。**这条路走不通**,两个原因:

1. 两台节点的运行时 iptables 都有 `-A BARONG_AWG -i awg0 -o awg0 -j DROP`——VPN 内
   部 peer 之间的流量是**被主动丢弃的**,这是当初有意设的安全规矩;
2. 两个节点的 `10.66.66.0/24` 各自独立分配、彼此完全隔离,节点间只有一条
   `permitopen="127.0.0.1:8765"` 的 SSH 管理桥,没有任何数据面互联。

所以没有去拆这道门,改用 WebRTC 自行协商通路,三级兜底:

1. 局域网 / 同网段直连(办公室内部,最快)
2. 公网 STUN 打洞直连(多数家宽和办公网可成)
3. TURN 中转(打不通时兜底;跨太平洋基本会落到这一档,预计半秒级延迟)

**VPN 开不开都不影响远程桌面**,两者互不依赖——设备 UUID 也是各发各的。

## TURN 中转

装在两台现有 VPN 节点上(`45.76.173.147` 洛杉矶 / `64.177.117.249` 芝加哥)。

```
/etc/turnserver.conf      配置(含共享密钥)
/etc/default/coturn       TURNSERVER_ENABLED=1
端口                       3478/udp, 3478/tcp, 50000-50100/udp(经 ufw 放行)
```

### 死规矩:配置文件权限必须是 `root:turnserver 640`

coturn 以低权用户 `turnserver` 运行。如果配置文件是 `600 root:root`,**它读不了自己
的配置,会静默回落到默认值,结果是一台开放中转**——任何人都能白嫖,而且所有
`denied-peer-ip` 规则一条都不生效。

2026-09-11 首次部署时踩过这个坑。`systemctl is-active` 会显示 `active`,STUN Binding
也照样成功,**看不出任何异常**。唯一能发现的办法是发一个不带凭据的 Allocate 请求:

```bash
# 必须被拒(401)。如果返回 0x0103 并给出中转地址,就是开放中转,立刻停服务。
.venv/bin/python scripts/rd_turn_probe.py 45.76.173.147
```

另一个旁证:分配到的中转端口如果**不在 50000-50100 之内**,说明配置没被读进去。

### 凭据

绝不下发 coturn 的静态口令。控制台按会话签 RFC 5766 短时凭据:

```
username   = "<到期时间戳>:<会话 id>"
credential = base64(HMAC-SHA1(static-auth-secret, username))
有效期      = 600 秒
```

后端配置项(`.env.production`):

```
RD_TURN_URLS=turn:45.76.173.147:3478,turn:64.177.117.249:3478
RD_TURN_SECRET=<与两台节点 /etc/turnserver.conf 的 static-auth-secret 一致>
```

**没配就只给 STUN**,打得通直连的照常用,打不通的会失败——这比假装配好了诚实。

### 中转看不见画面

WebRTC 媒体是 DTLS-SRTP 端到端加密的。中转节点只转发密文,解不开,看不到屏幕内容。

## 同意机制:门在哪

**门不在控制台,在被控机本地。**

- 同意框是 Electron 主进程的原生 `dialog`,不是网页弹窗——网页弹窗能被脚本自动点掉;
- 主进程自己拿会话 cookie 去后端回报同意,**网页手里没有任何能表达「已同意」的动作**;
- 免同意的会话(自己的机器 / 公用机)主进程没亲手批准过,交出屏幕之前会自己再去后端
  `GET /rd/sessions/{id}` 核实一次;
- 屏幕捕获的闸门焊在主进程的 `setDisplayMediaRequestHandler` 里,没有活会话就直接拒,
  网页连屏幕 id 都拿不到;
- 会话期间屏幕上挂一条永久红色横条,点「立即断开」随时踢人。

这三条各自配了源码断言(`tests/frontend/rd-remote-desktop.test.mjs`、
`windows/console-app/test/security-source.test.cjs`),防止以后被顺手改掉。**网页上永远
不该出现一个「同意」按钮。**

## 上限

| 承诺 | 上限 | 机制在哪 |
|---|---|---|
| 同意框没人理不会一直占着机器 | 60 秒 | `sweep_stale()`,挂在读路径开头,不靠后台任务 |
| 同意了但画面一直不通,不会把被控机占住 | 前端 45 秒自己收场;后端 90 秒兜底判 `handshake_failed` | `RD_HANDSHAKE_TIMEOUT_MS`(webrtc.ts)+ `sweep_stale()` |
| 建连路上一次网络抖动不会让整场作废 | 每个关键请求最多试 4 次(0/1/2/4 秒退避) | `withRdRetry()`(api.ts) |
| 单场会话不会无限久 | 2 小时 | 同上 |
| 公用机名单不会无限大 | 每台 10 人 | `grant_unattended()` |
| TURN 凭据不会长期有效 | 600 秒 | 签名里带到期时间戳,coturn 自己判 |
| 中转不会打爆小节点 | 每节点 5 路 | 后端发起时计数 + coturn `total-quota=20` 兜底 |

## 发版顺序(不能反)

1. **backend**(新迁移 `20260911_03_rd_remote_desktop`;先查 `git status` 和 `alembic heads`)
2. **frontend**
3. **nginx** reload(`/api/backend/rd/stream` 的 SSE location,少了它握手会被缓冲卡死)
4. 最后才把 `BarongOpsConsoleSetup-0.4.0-pilot-x64.exe` + `.blockmap` + `latest.yml`
   放进 `releases/windows/`

**顺序反了的后果**:客户端先更新,会打开一个后端还没有 `/rd/*` 的页面。

客户端更新不需要卸载重装:0.3.1 自带 electron-updater,登录后 30 秒内自检,下载完弹
框问「现在重启安装 / 下次打开时安装」。

## 验收(只认与实现无关的事实)

「代码写了 / 测试绿了 / 日志没报错」都不算。

1. 两台真机之间真连通:一台装 0.4.0 当被控端,另一台用浏览器当控制端,发起 → 被控端
   弹**原生**框 → 同意 → 画面出来 → 鼠标能点开被控机上的记事本并打出字。截图为证。
2. 拒绝路径:点「拒绝」后控制端明确收到被拒,且 `rd_sessions` 该行 `state='denied'`。
3. 台账:直接查库,`started_at` / `ended_at` 与实际操作时长吻合。
4. 踢人:点红条上的断开,控制端画面 1 秒内停住。
5. 公用机:标记时在本机弹原生确认;标完后名单内的人不弹框,名单外的人照样弹框。
6. 自动更新:拿一台装着 0.3.1 的机器,登录后不做任何手动操作,确认它自己升到 0.4.0。
7. TURN 不是开放中转:见上面「死规矩」那一节的探测命令。

## 2026-09-18 真机首测失败复盘

现象:请求、同意都正常,同意后发起端没出画面,过了好一阵显示连接失败。

查到的事实(nginx 日志 + `rd_signals` 表 + `auth_sessions`):

- 发起端(用户机,客户端 0.3.0)10:03:33 拿到 ICE 配置后,**再没有任何一条请求到达服务器**
  ——offer、结束回报、15 秒一次的列表刷新、信令流重连全都没有;`rd_signals` 该会话零行。
- 服务器那头没断:发起端的信令流在 10:04:07 被后端按 55 秒寿命正常关闭(200,不是 499)。
- 同一出口 IP(139.209.9.230)下王创鑫的两台设备同时段请求照常。
- 日志里同时段出现的 45.76.173.147(洛杉矶 VPN 节点)是**王创鑫另一台挂着 VPN 的设备**
  (auth_sessions 可证),与发起端无关。初判「发起端连上了 VPN」是把两台设备混了,已更正。
- 发起端页面最后显示的是「建立连接失败。」——即 offer 请求在本机卡住、超时后才报错。

**发起端本机为什么请求出不去,服务器侧看不到,尚未定论。** 候选:本机到服务器的那条
长连接被静默掐断(HTTP/2 所有请求共用一条 TCP)、或 0.3.0 客户端页面异常。下次复测前
要先在页面里加分步诊断,才能从本机侧拿到证据。

不论根因是什么,当时的代码对建连请求只试一次、失败连「结束」也没报上去,于是:

- 被控机上那条会话以「已同意」挂了两小时(后端只对 2 小时封顶),期间谁都连不上它;
- 被控端红条不撤,因为网页从不处理自己那场会话的结束;
- 顺带查出:SSE 只查活会话,**被拒/结束从来推不出去**;流 55 秒重开会把 offer 重放,
  被控端会再抓一次屏再答一次;还没答的请求重开流后会再弹一次原生同意框。

以上全部修掉,每条配了测试。

## 建连黑匣子(`rd_client_traces`)

两端页面把建连的每一步先记在本机 localStorage,再补传到 `POST /rd/diagnostics`;网络
断着就攒着,恢复或下次打开页面时再传。补传**故意绕开 apiRequest 的 6 路排队**,页面自己
的请求层卡死时也能把话传出去。只记步骤/耗时/错误名/状态,不记 SDP 和候选地址。

上限:一次 ≤ 200 条、本机最多攒 600 条、每人每小时 ≤ 3000 条(超了整批拒收,客户端留着
晚点传)、服务器留 14 天。`(client_id, seq)` 唯一,重传不重复入库。

读法(一场会话的两端时间线,`ctl.*` 是发起端、`agt.*` 是被控端):

```sql
select client_at at time zone 'UTC' as t, received_at - client_at as late,
       u.username, client_label, step, detail
from rd_client_traces t join users u on u.id = t.user_id
where session_id = '<会话 id>' or (client_id in (
      select client_id from rd_client_traces where session_id = '<会话 id>')
      and client_at between <开始> and <结束>)
order by client_at, seq;
```

看点:`tick` 的 `gap_ms` 远大于 3000 = 页面主线程卡过;`*_fail` 里的 `queued` 很大 = 请求在
页面里排队没出去;`late`(补传延迟)很大 = 当时本机确实传不出来。

## 已知限制(不藏着)

- **安装包没有代码签名**(既有状态,本期未改变)。更新链靠 `latest.yml` 的 SHA-512 +
  TLS + 会话 cookie 闸,不是证书信任链;Windows SmartScreen 每次安装都会警告。
- UAC 提权窗口和锁屏界面**抓不到也控不了**(Windows 安全桌面限制,所有用户态远程桌面
  软件都一样)。
- 跨太平洋会走 TURN 中转绕美国,预计半秒级延迟。实测之后再决定要不要加香港节点。
- 第一期不做:剪贴板互通、文件传输、多显示器切换、会话录像、Mac/安卓被控端。
