# Barong Ops Console 空地基蓝图 V1

## 1. 系统总定位

Barong Ops Console 是 Barong Yekhna 独立站自动化运营系统的统一操作界面、状态总控层、任务调度中心、资产索引中心、审核决策中心、日志报告中心和未来功能扩展底座。

它不是白苏婉企业微信机器人的升级版，不是聊天窗口，也不是普通 Dashboard。

控制台优先使用结构化基础功能，例如：
- 新产品建档固定表单
- 字段校验
- 任务按钮
- 审核按钮
- 报告入口
- 日志查看
- 状态追踪

只有需要 AI 生成、分析、判断、补全、润色、审核建议时，才调用机器人模块。

当前白苏婉企业微信任务可以废除。未来如果保留白苏婉，只作为控制台中的产品架构 / 产品资料标准化 / AI 辅助分析模块，不再作为系统主入口。

## 2. 系统边界

- 控制台：统一入口、统一状态、统一任务、统一日志、统一报告、统一审核。
- n8n：执行引擎，不作为长期记忆中心。
- 数据库：状态真相源和长期记忆本体。
- AI 机器人：生成、分析、建议、辅助审核，不直接决定核心状态。
- Filebrowser / MinIO：资产仓库。
- 企业微信：只负责通知和告警，不承担复杂任务入口。
- WooCommerce：外部发布目标，必须通过受控执行工作流调用。

## 3. 机器人和工作流积木式接入

所有机器人、工作流和自动化系列都必须通过注册机制接入控制台。

必须存在：
- Module Registry
- Agent Registry
- Workflow Registry
- Job Manager

每个系列有 module_id。
每个机器人有 agent_id。
每个工作流有 workflow_id。
每个任务有 job_id。

新增机器人、新系列、新功能时，不允许硬编码补丁式接入，必须登记：
- 职责
- 输入 schema
- 输出 schema
- 权限
- 风险等级
- 可调用工作流
- 版本
- 状态
- 依赖
- 产物类型
- 审核项类型
- 错误码

普通机器人不能直接写数据库，也不能触发高风险动作。只有经过控制台授权的执行型工作流 / API 可以写数据库，并且必须留下操作日志、任务日志和错误记录。

## 4. 数据库与 DeepSeek 记忆机器人

数据库是系统长期记忆本体和事实真相源。

DeepSeek 记忆机器人只作为低成本记忆检索、上下文组装、跨模块总结、错误归因、历史复盘和任务调度辅助层。

DeepSeek 默认只读，可以生成摘要和 Context Packet，但不能直接修改：
- 产品核心状态
- 任务状态
- 审核结论
- 发布状态
- WooCommerce 数据
- Product_Knowledge
- 系统设置

所有核心状态写入必须通过控制台授权 API。

必须设计：
- memory_events
- context_packets
- memory_summaries
- agent_memory_access_logs

所有重要事件都要写入 memory_events，例如：
- 新产品创建
- 字段更新
- 任务启动
- 任务完成
- 任务失败
- 文件生成
- 审核通过
- 审核驳回
- 错误修复
- 发布完成
- 系统原则变更

每个工作流启动前应请求 Context Packet。
每个工作流结束后必须回写 job 结果、artifact、error 和 memory_event。

## 5. 板块化与隔离运行

控制台必须采用板块化架构，默认未来会持续新增大量新板块、新机器人、新工作流和新外部系统。

新增板块时应该增加“配置和注册”，而不是修改“控制台核心”。

每个板块必须通过 Module Contract / Module Registry 接入，声明：
- 模块 ID
- 模块名称
- 模块职责
- 不负责事项
- 输入 schema
- 输出 schema
- 读写权限
- 可运行模式
- 前置条件
- 下游触发条件
- 失败影响范围
- 日志规则
- 版本
- 健康检查
- 回滚规则
- 是否允许自动化

模块之间默认互不干预，只能通过以下机制协作：
- Job Manager
- 数据库状态机
- artifact
- review item
- memory_event
- Context Packet
- 标准 API

禁止跨模块直接改状态。
禁止跨模块直接读临时文件。
禁止下游读取未完成任务结果。
禁止 silent success。
禁止隐形兜底。
禁止自动跨越人工审核。
禁止一个模块既生成又批准自己。
禁止未注册模块运行。
禁止直接触发高风险动作。

## 6. 施工路线

采用“先地基、后板块、逐个接入”的方式。

第一阶段只建设控制台空地基，包括：
- 模块注册
- 任务中心
- 日志错误
- 资产登记
- 审核中心
- 记忆事件
- 基础数据库
- 基础前后端
- 健康检查

空地基阶段不接入复杂真实业务。
最多接一个假测试任务，用来证明控制台能创建任务、写日志、登记状态、展示结果。

之后每个新业务板块必须：
1. 单独设计
2. 单独开发
3. 单独测试
4. 单独验收
5. 再通过注册机制接入控制台

一个板块失败，只影响自身任务和明确关联下游，不得污染全局系统。

## 7. Codex 施工铁律

Codex 只能在 /opt/barong-ops-console 内施工，除非明确批准。

禁止修改：
- /opt/n8n
- /opt/filebrowser
- /opt/minio
- /root
- 任何现有生产 docker-compose 文件

禁止：
- 停止生产容器
- 重启生产容器
- 删除生产文件
- 读取或打印真实密钥
- 直接连接真实 WooCommerce 执行写操作
- 在空地基完成前添加真实业务模块

每个 Codex 任务必须：
1. 先输出 plan
2. 限定允许修改目录
3. 限定禁止修改目录
4. 输出 changed files
5. 提供 verification steps
6. 更新文档或 changelog
7. 不得跨任务顺手扩展功能
